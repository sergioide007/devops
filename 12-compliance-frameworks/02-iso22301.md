# ISO 22301 — Business Continuity Management System (BCMS)

> ISO 22301 answers one question: "What happens when things go wrong?"
> When a data center fails, a cyberattack hits, or a pandemic stops your team —
> your business must keep running. DevOps engineers build the technical foundation
> for business continuity.

---

## What Is ISO 22301?

```
ISO 22301 = A framework for keeping the business running during disruptions

Key terms:
  BCP   = Business Continuity Plan (the plan)
  BCM   = Business Continuity Management (the process)
  DR    = Disaster Recovery (technical recovery)
  RTO   = Recovery Time Objective (HOW FAST must you recover?)
  RPO   = Recovery Point Objective (HOW MUCH DATA can you lose?)

Example for a payment system:
  RTO = 4 hours     → Must be back online within 4 hours
  RPO = 15 minutes  → Can only lose 15 minutes of transactions
  
This drives technical decisions:
  RPO 15 min → need near-real-time replication (not daily backup)
  RTO 4 hours → need automated failover (not manual restore)
```

## RTO/RPO Technical Requirements Map

```
          │  Low Cost               │  High Cost
          │  (Simple)               │  (Complex)
──────────┼─────────────────────────┼────────────────────────────
RPO: days │  Daily backup to S3     │  Over-engineering
          │  Manual restore         │
──────────┼─────────────────────────┼────────────────────────────
RPO: hrs  │  RDS automated backups  │  Aurora read replica
          │  S3 versioning          │  
──────────┼─────────────────────────┼────────────────────────────
RPO: min  │  RDS Multi-AZ           │  Aurora Global Database
          │  (1-2 min failover)     │  (< 1 sec replication)
──────────┼─────────────────────────┼────────────────────────────
RPO: secs │  Synchronous replication│  Active-active multi-region
          │  (expensive)            │  (very expensive)
──────────┴─────────────────────────┴────────────────────────────

RTO  │  Hours    │  Minutes      │  Seconds
─────┼───────────┼───────────────┼─────────────────────────────
DR   │  Restore  │  Pilot light  │  Warm standby   │  Multi-site
     │  from S3  │  (minimal AWS)│  (scaled down)  │  active-active
─────┼───────────┼───────────────┼─────────────────┼─────────────
Cost │  $        │  $$           │  $$$            │  $$$$
```

## DR Strategies — From Cheapest to Best

### Strategy 1: Backup and Restore (RTO: hours, RPO: hours)

```bash
#!/bin/bash
# dr-backup-restore.sh
# Cheapest DR strategy — backup everything to S3

S3_BACKUP_BUCKET="company-disaster-recovery"
REGION="us-east-1"
DR_REGION="us-west-2"  # different region for real disaster recovery

echo "=== ISO 22301 Backup Job - $(date) ==="

# 1. Database backup (RDS snapshot)
DB_INSTANCE="production-postgres"
SNAPSHOT_ID="dr-backup-$(date +%Y%m%d-%H%M)"

echo "Creating RDS snapshot: $SNAPSHOT_ID"
aws rds create-db-snapshot \
  --db-instance-identifier $DB_INSTANCE \
  --db-snapshot-identifier $SNAPSHOT_ID \
  --region $REGION

# Wait for snapshot completion
aws rds wait db-snapshot-completed \
  --db-snapshot-identifier $SNAPSHOT_ID \
  --region $REGION

# Copy snapshot to DR region
echo "Copying snapshot to DR region..."
aws rds copy-db-snapshot \
  --source-db-snapshot-identifier \
    "arn:aws:rds:$REGION:$(aws sts get-caller-identity --query Account --output text):snapshot:$SNAPSHOT_ID" \
  --target-db-snapshot-identifier $SNAPSHOT_ID \
  --region $DR_REGION

# 2. Application state backup (configs, secrets references)
echo "Backing up application configs..."
aws s3 sync /opt/apps/configs/ \
  s3://$S3_BACKUP_BUCKET/configs/$(date +%Y%m%d)/ \
  --region $REGION \
  --sse AES256

# Copy to DR region bucket
aws s3 sync \
  s3://$S3_BACKUP_BUCKET/ \
  s3://$S3_BACKUP_BUCKET-dr/ \
  --source-region $REGION \
  --region $DR_REGION

# 3. Verify backup
echo "Verifying backup integrity..."
SNAPSHOT_STATUS=$(aws rds describe-db-snapshots \
  --db-snapshot-identifier $SNAPSHOT_ID \
  --region $DR_REGION \
  --query 'DBSnapshots[0].Status' \
  --output text)

if [ "$SNAPSHOT_STATUS" = "available" ]; then
  echo "✅ Backup SUCCESS: snapshot available in $DR_REGION"
else
  echo "❌ Backup FAILED: snapshot status = $SNAPSHOT_STATUS"
  # Alert on-call team
  aws sns publish \
    --topic-arn arn:aws:sns:$REGION:$(aws sts get-caller-identity --query Account --output text):oncall-alerts \
    --message "DR Backup FAILED: $SNAPSHOT_ID in $DR_REGION"
  exit 1
fi

echo "Backup completed: $(date)"
```

### Strategy 2: Pilot Light (RTO: 30-60 min, RPO: minutes)

```hcl
# terraform/dr-pilot-light.tf
# Pilot light: minimal infrastructure always running in DR region
# Data is synced. Compute is off (or minimal). Scale up when needed.

terraform {
  required_providers {
    aws = { source = "hashicorp/aws" }
  }
}

provider "aws" {
  alias  = "primary"
  region = "us-east-1"
}

provider "aws" {
  alias  = "dr"
  region = "us-west-2"  # DR region
}

# PRIMARY: Full Aurora cluster
resource "aws_rds_cluster" "primary" {
  provider              = aws.primary
  cluster_identifier    = "production-cluster"
  engine                = "aurora-postgresql"
  engine_version        = "15.4"
  database_name         = "appdb"
  master_username       = "admin"
  manage_master_user_password = true

  # Point-in-time recovery
  backup_retention_period = 7
  preferred_backup_window = "02:00-03:00"
  
  enabled_cloudwatch_logs_exports = ["postgresql"]
  
  tags = { Environment = "production", ISO22301 = "primary" }
}

# DR: Aurora Global Cluster (data replicates < 1 second to DR)
resource "aws_rds_global_cluster" "main" {
  global_cluster_identifier = "company-global-cluster"
  engine                    = "aurora-postgresql"
  engine_version            = "15.4"
  database_name             = "appdb"
  storage_encrypted         = true
}

# DR cluster (secondary — always up, always synced)
resource "aws_rds_cluster" "dr" {
  provider                   = aws.dr
  cluster_identifier         = "dr-cluster"
  engine                     = "aurora-postgresql"
  engine_version             = "15.4"
  global_cluster_identifier  = aws_rds_global_cluster.main.id
  
  # DR has ONE instance (pilot light — minimal cost)
  # On failover: scale up to match primary
  
  skip_final_snapshot = false
  tags = { Environment = "dr", ISO22301 = "pilot-light" }
}

resource "aws_rds_cluster_instance" "dr_instance" {
  provider           = aws.dr
  cluster_identifier = aws_rds_cluster.dr.id
  instance_class     = "db.t3.medium"  # Small — scale up on DR activation
  engine             = "aurora-postgresql"
  
  tags = { ISO22301 = "pilot-light-instance" }
}

# DR: EKS Cluster (exists but scaled to 0 nodes)
resource "aws_eks_cluster" "dr" {
  provider = aws.dr
  name     = "dr-cluster"
  role_arn = aws_iam_role.eks_dr.arn

  vpc_config {
    subnet_ids = aws_subnet.dr_private[*].id
  }
}

# Node group starts at 0 — scale up on DR activation
resource "aws_eks_node_group" "dr" {
  provider        = aws.dr
  cluster_name    = aws_eks_cluster.dr.name
  node_group_name = "dr-nodes"
  node_role_arn   = aws_iam_role.eks_node_dr.arn
  subnet_ids      = aws_subnet.dr_private[*].id
  instance_types  = ["t3.large"]

  scaling_config {
    desired_size = 0  # Zero nodes in normal operation (pilot light)
    max_size     = 10
    min_size     = 0
  }
}
```

### Strategy 3: Warm Standby (RTO: minutes, RPO: seconds)

```yaml
# kubernetes/dr-warm-standby.yml
# Warm standby: reduced capacity always running in DR region
# On disaster: scale up to full capacity (minutes, not hours)

# ArgoCD ApplicationSet — deploy to BOTH primary and DR
apiVersion: argoproj.io/v1alpha1
kind: ApplicationSet
metadata:
  name: payment-api-multi-region
  namespace: argocd
spec:
  generators:
    - list:
        elements:
          - cluster: primary
            url: https://primary-eks.example.com
            namespace: production
            replicas: "5"
          - cluster: dr
            url: https://dr-eks.example.com
            namespace: production
            replicas: "2"  # Warm standby: 2 replicas (not 5)
  template:
    metadata:
      name: 'payment-api-{{cluster}}'
    spec:
      project: default
      source:
        repoURL: https://github.com/company/gitops
        targetRevision: HEAD
        path: apps/payment-api
        helm:
          parameters:
            - name: replicaCount
              value: '{{replicas}}'
            - name: environment
              value: '{{cluster}}'
      destination:
        server: '{{url}}'
        namespace: '{{namespace}}'
      syncPolicy:
        automated:
          prune: true
          selfHeal: true
```

## DR Runbook — Automated Failover

```bash
#!/bin/bash
# dr-failover-runbook.sh
# ISO 22301 — Disaster Recovery Activation Procedure
# This script is your DR runbook. Keep it tested and updated.

set -euo pipefail

DR_REGION="us-west-2"
PRIMARY_REGION="us-east-1"
GLOBAL_CLUSTER="company-global-cluster"

echo "====================================================="
echo "ISO 22301 DISASTER RECOVERY ACTIVATION"
echo "Date: $(date)"
echo "Triggered by: $USER"
echo "====================================================="

# STEP 1: Confirm with operator
echo ""
echo "⚠️  WARNING: This will activate DISASTER RECOVERY mode"
echo "Primary region: $PRIMARY_REGION (FAILING)"
echo "DR region: $DR_REGION (ACTIVATING)"
echo ""
read -p "Type 'ACTIVATE DR' to confirm: " CONFIRM
if [ "$CONFIRM" != "ACTIVATE DR" ]; then
  echo "Aborted."
  exit 1
fi

# STEP 2: Update Route 53 DNS (move traffic to DR)
echo ""
echo "STEP 1: Updating DNS to point to DR region..."

# Get current DR load balancer DNS
DR_ALB=$(aws elbv2 describe-load-balancers \
  --region $DR_REGION \
  --query 'LoadBalancers[?Scheme==`internet-facing`].DNSName' \
  --output text)

# Update Route 53 health-check policy
aws route53 change-resource-record-sets \
  --hosted-zone-id Z1234567890 \
  --change-batch '{
    "Changes": [{
      "Action": "UPSERT",
      "ResourceRecordSet": {
        "Name": "api.company.com",
        "Type": "CNAME",
        "TTL": 60,
        "ResourceRecords": [{"Value": "'$DR_ALB'"}]
      }
    }]
  }'

echo "✅ DNS updated to DR ALB: $DR_ALB"

# STEP 3: Promote Aurora Global Cluster
echo ""
echo "STEP 2: Promoting Aurora to DR region..."

aws rds remove-from-global-cluster \
  --global-cluster-identifier $GLOBAL_CLUSTER \
  --db-cluster-identifier "arn:aws:rds:$DR_REGION:$(aws sts get-caller-identity --query Account --output text):cluster:dr-cluster" \
  --region $DR_REGION

# Wait for promotion
echo "Waiting for DB promotion (may take 1-2 minutes)..."
aws rds wait db-cluster-available \
  --db-cluster-identifier dr-cluster \
  --region $DR_REGION

echo "✅ Aurora promoted to writer in $DR_REGION"

# STEP 4: Scale up DR Kubernetes nodes
echo ""
echo "STEP 3: Scaling up DR Kubernetes cluster..."

aws eks update-nodegroup-config \
  --cluster-name dr-cluster \
  --nodegroup-name dr-nodes \
  --scaling-config minSize=3,maxSize=10,desiredSize=5 \
  --region $DR_REGION

echo "Waiting for nodes to join cluster..."
# Wait for nodes to be Ready
timeout 300 bash -c 'until kubectl --context dr-cluster get nodes | grep -q "Ready"; do sleep 10; done'

echo "✅ DR Kubernetes cluster scaled up"

# STEP 5: Verify services are healthy
echo ""
echo "STEP 4: Verifying services in DR region..."

kubectl --context dr-cluster get pods -n production
kubectl --context dr-cluster get services -n production

# Health check
HEALTH=$(curl -sf https://api.company.com/health | jq '.status')
if [ "$HEALTH" = '"ok"' ]; then
  echo "✅ Service health check PASSED"
else
  echo "❌ Service health check FAILED — investigate"
fi

# STEP 6: Notify stakeholders
echo ""
echo "STEP 5: Notifying stakeholders..."

aws sns publish \
  --topic-arn arn:aws:sns:$DR_REGION:$(aws sts get-caller-identity --query Account --output text):dr-notifications \
  --message "DR ACTIVATED: Traffic now routed to $DR_REGION. RTO achieved. Timestamp: $(date)" \
  --subject "DISASTER RECOVERY ACTIVATED"

echo ""
echo "====================================================="
echo "DISASTER RECOVERY ACTIVATION COMPLETE"
echo "RTO target: 30 minutes"
echo "Actual time: $(date)"
echo ""
echo "NEXT STEPS:"
echo "1. Monitor https://grafana.company.com for errors"
echo "2. Notify customers if SLA breach"
echo "3. Investigate primary region failure"
echo "4. Plan failback when primary is restored"
echo "====================================================="
```

## BIA Template — ISO 22301

### System: Payment Processing API

| Impact Category | 1 Hour | 4 Hours | 24 Hours | 1 Week |
|----------------|--------|---------|----------|--------|
| Revenue loss ($) | $50,000 | $200,000 | $1.2M | $8.4M |
| Transactions affected | 3,000 | 12,000 | 72,000 | 504,000 |

| Customer trust | Low | Medium | High | Critical |

- Maximum Tolerable Downtime (MTD): 4 hours

## ISO 22301 Testing — DR Exercises

```bash
#!/bin/bash
# dr-test-exercise.sh
# ISO 22301 requires you to TEST your DR plan regularly
# Run this quarterly (or after major infrastructure changes)

echo "=== DR Exercise — $(date) ==="
echo "ISO 22301 Section 8.5: Testing and Exercises"
echo ""

# Test 1: Backup Restoration Test
echo "TEST 1: Backup Restoration"
echo "Testing: Can we restore from yesterday's backup?"

YESTERDAY_SNAPSHOT=$(aws rds describe-db-snapshots \
  --db-instance-identifier production-postgres \
  --query 'DBSnapshots | sort_by(@, &SnapshotCreateTime) | [-1].DBSnapshotIdentifier' \
  --output text)

# Restore to test instance
aws rds restore-db-instance-from-db-snapshot \
  --db-instance-identifier dr-test-restore \
  --db-snapshot-identifier $YESTERDAY_SNAPSHOT \
  --db-instance-class db.t3.medium

aws rds wait db-instance-available \
  --db-instance-identifier dr-test-restore

echo "✅ TEST 1 PASSED: Backup restored in $(date)"

# Clean up test instance
aws rds delete-db-instance \
  --db-instance-identifier dr-test-restore \
  --skip-final-snapshot

# Test 2: DNS Failover Test
echo ""
echo "TEST 2: DNS Failover Speed"
echo "Testing: How fast does DNS update on failover?"

START_TIME=$(date +%s)
# Simulate failover (update to DR temporarily)
# ... (run failover, verify, run failback)
END_TIME=$(date +%s)
ELAPSED=$((END_TIME - START_TIME))

echo "DNS failover time: ${ELAPSED}s (target: < 60s)"
if [ $ELAPSED -lt 60 ]; then
  echo "✅ TEST 2 PASSED"
else
  echo "❌ TEST 2 FAILED — exceeds target TTL"
fi

# Test 3: Recovery Validation
echo ""
echo "TEST 3: End-to-End Service Validation"

ENDPOINTS=(
  "https://api.company.com/health"
  "https://api.company.com/v1/status"
  "https://api.company.com/v1/payments/test"
)

for endpoint in "${ENDPOINTS[@]}"; do
  STATUS=$(curl -sf -o /dev/null -w "%{http_code}" "$endpoint")
  if [ "$STATUS" = "200" ]; then
    echo "✅ $endpoint → HTTP $STATUS"
  else
    echo "❌ $endpoint → HTTP $STATUS (FAILED)"
  fi
done

# Generate exercise report
cat > "dr-exercise-report-$(date +%Y%m%d).md" << EOF
# DR Exercise Report
Date: $(date)
Conducted by: $USER

## Tests Performed
- [x] Backup restoration test
- [x] DNS failover speed test  
- [x] End-to-end service validation

## Results
- RTO achieved: ${ELAPSED}s (target: 30 min)
- All health checks: PASSED
- Data integrity: VERIFIED

## Findings
(none this exercise)

## Next Exercise Date
$(date -d '+3 months' +%Y-%m-%d)

## ISO 22301 Clause: 8.5 — Exercising and Testing
EOF

echo ""
echo "Exercise report: dr-exercise-report-$(date +%Y%m%d).md"
```

## Multi-Region Architecture (Active-Active)

```hcl
# terraform/active-active-multiregion.tf
# Highest DR level — run in two regions simultaneously
# RTO: 0 (no failover needed — always running)
# RPO: 0 (synchronous replication)

# Route 53 latency-based routing (sends traffic to closest region)
resource "aws_route53_record" "api_primary" {
  zone_id = aws_route53_zone.main.zone_id
  name    = "api.company.com"
  type    = "A"

  alias {
    name                   = aws_lb.primary.dns_name
    zone_id                = aws_lb.primary.zone_id
    evaluate_target_health = true
  }

  set_identifier = "primary"
  
  latency_routing_policy {
    region = "us-east-1"
  }

  health_check_id = aws_route53_health_check.primary.id
}

resource "aws_route53_record" "api_dr" {
  provider = aws.dr
  zone_id  = aws_route53_zone.main.zone_id
  name     = "api.company.com"
  type     = "A"

  alias {
    name                   = aws_lb.dr.dns_name
    zone_id                = aws_lb.dr.zone_id
    evaluate_target_health = true
  }

  set_identifier = "dr"

  latency_routing_policy {
    region = "us-west-2"
  }

  health_check_id = aws_route53_health_check.dr.id
}

# Health check — Route 53 auto-removes unhealthy region
resource "aws_route53_health_check" "primary" {
  fqdn              = aws_lb.primary.dns_name
  port              = 443
  type              = "HTTPS"
  resource_path     = "/health"
  failure_threshold = 3
  request_interval  = 10

  tags = { ISO22301 = "health-check-primary" }
}
```

## Interview Questions — ISO 22301

**Q: What is the difference between RTO and RPO?**
```
RTO = Recovery Time Objective
  "How long can the business survive without the system?"
  Example: 4 hours → system must be back online within 4 hours

RPO = Recovery Point Objective  
  "How much data can we afford to lose?"
  Example: 15 minutes → we might lose 15 minutes of transactions

They drive DIFFERENT technical decisions:
  RPO 15 min → need near-real-time replication (database mirroring)
  RTO 4 hours → need automated failover (not manual restore)
```

**Q: What DR strategy would you choose for a bank's core system?**
```
Core banking: RTO < 1 hour, RPO < 5 minutes

→ Warm Standby with Aurora Global Database
  - Aurora Global: < 1 second replication to DR region
  - Kubernetes warm standby: 2 replicas in DR (scale to 10 on failover)
  - Route 53 health checks: auto-failover in 60 seconds
  - Cost: ~$3,000-5,000/month extra (justified for core banking)
  
NOT active-active (too expensive for most banks)
NOT pilot light (too slow for banking regulations)
```
