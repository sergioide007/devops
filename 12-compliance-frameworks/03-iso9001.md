# ISO 9001 — Quality Management System (QMS)

> ISO 9001 is about quality — ensuring your product works as the customer expects.
> In DevOps, your CI/CD pipeline IS your quality management system.
> Every test, every code review, every quality gate is an ISO 9001 control.

---

## What Is ISO 9001?

```
ISO 9001 = Framework for consistently delivering quality products/services

Key principle: PDCA cycle
  Plan  → Define quality objectives and processes
  Do    → Execute the processes (CI/CD pipelines)
  Check → Monitor and measure (tests, metrics, reviews)
  Act   → Improve based on findings (retrospectives, changes)

In DevOps terms:
  Plan  = Sprint planning + acceptance criteria + definition of done
  Do    = Development + CI/CD pipeline execution
  Check = Tests, code review, quality gates, monitoring
  Act   = Retrospective + pipeline improvements + incident reviews
```

## ISO 9001:2015 Clauses — DevOps Mapping

```
CLAUSE 4 — Context of the Organization
  → Define what quality means for YOUR system
  → Identify stakeholders (customers, regulators, internal teams)

CLAUSE 5 — Leadership
  → Management must commit to quality
  → DevOps: Director/VP approves quality gates and SLOs

CLAUSE 6 — Planning
  → Risk-based thinking (FMEA, threat modeling)
  → Quality objectives with measurable targets
  → DevOps: DORA metrics as quality objectives

CLAUSE 7 — Support
  → Competence: team must be trained
  → Documentation: runbooks, architecture docs, ADRs
  → DevOps: wikis, confluence, README files, code comments

CLAUSE 8 — Operation  ← MOST RELEVANT FOR DEVOPS
  8.1  → Operational planning (CI/CD pipeline design)
  8.3  → Design and development (SDLC with quality gates)
  8.4  → Control of externally provided services (vendors, cloud providers)
  8.5  → Production and service provision (deployments, incidents)
  8.6  → Release of products (deployment gates, approval workflows)
  8.7  → Nonconforming outputs (bug management, incident response)

CLAUSE 9 — Performance Evaluation
  → Monitoring, measurement, analysis
  → Internal audit
  → Management review
  → DevOps: Grafana dashboards, SLO reports, quarterly reviews

CLAUSE 10 — Improvement
  → Corrective action (incident postmortems)
  → Continual improvement (retrospectives, DORA metric trends)
```

## Clause 8.3 — Design and Development (SDLC Quality Gates)

```yaml
# The CI/CD pipeline as ISO 9001 quality system
# Every stage is a quality gate

name: ISO 9001 Quality Pipeline

stages:
  # GATE 1: Code Quality (Clause 8.3.4 — Design/Dev Controls)
  - name: Code Review
    required_approvals: 2
    checklist:
      - Requirements traceability (does this code match the ticket?)
      - Unit tests coverage > 80%
      - No critical SonarQube issues
      - API documentation updated
    evidence: "GitHub PR with approvals"

  # GATE 2: Automated Testing (Clause 8.3.5 — Design/Dev Outputs)
  - name: Automated Test Suite
    tests:
      unit:
        coverage_threshold: 80%
        framework: "jest / pytest / junit"
      integration:
        scope: "API endpoints + database"
        framework: "supertest / pytest-httpx"
      contract:
        scope: "API contracts between services"
        framework: "Pact (consumer-driven)"
      performance:
        p95_latency_max: 500ms
        error_rate_max: 0.1%
    fail_on: "any test failure"

  # GATE 3: Security Quality (Clause 8.3.3 — Design Inputs)
  - name: Security Scan
    tools:
      - SonarQube SAST (code)
      - Trivy (container)
      - OWASP ZAP (API)
    fail_on: "CRITICAL or HIGH severity"

  # GATE 4: Staging Validation (Clause 8.6 — Release)
  - name: Staging Deployment + Smoke Tests
    environment: staging
    smoke_tests:
      - health check passes
      - login works
      - critical user journey works
    required_for_release: true

  # GATE 5: Change Approval (Clause 8.6 — Release Authorization)
  - name: Change Advisory Board (CAB)
    required_for: ["production", "major releases"]
    approvers: ["Tech Lead", "QA Manager", "Ops Manager"]
    evidence: "Jira change ticket with approvals"
```

## DORA Metrics as ISO 9001 Quality Objectives

```python
#!/usr/bin/env python3
# dora-metrics.py
# ISO 9001 Clause 6.2: Quality objectives shall be measurable
# DORA metrics are the measurable quality objectives for DevOps

import boto3
import json
from datetime import datetime, timedelta

def get_dora_metrics(days: int = 30) -> dict:
    """
    Calculate DORA metrics for ISO 9001 quality reporting.
    
    DORA Metrics:
    1. Deployment Frequency    → How often do you ship?
    2. Lead Time for Changes   → How fast from commit to production?
    3. Mean Time to Recovery   → How fast do you recover?
    4. Change Failure Rate     → What % of deployments cause incidents?
    """
    
    end_date = datetime.now()
    start_date = end_date - timedelta(days=days)
    
    # Get deployments from CodePipeline
    codepipeline = boto3.client('codepipeline')
    
    # 1. DEPLOYMENT FREQUENCY
    executions = codepipeline.list_pipeline_executions(
        pipelineName='production-pipeline',
        maxResults=100
    )
    
    successful_deploys = [
        e for e in executions['pipelineExecutionSummaries']
        if e['status'] == 'Succeeded'
        and start_date <= e['lastUpdateTime'].replace(tzinfo=None) <= end_date
    ]
    
    deployment_frequency = len(successful_deploys) / days
    
    # Classify (DORA Research Benchmarks)
    if deployment_frequency >= 1:
        df_level = "Elite (multiple deploys/day)"
    elif deployment_frequency >= (1/7):
        df_level = "High (1-7 times/week)"
    elif deployment_frequency >= (1/30):
        df_level = "Medium (1-4 times/month)"
    else:
        df_level = "Low (less than once/month)"
    
    # 2. LEAD TIME (commit to production)
    # Use CodeCommit/GitHub API to get PR merge times vs deploy times
    lead_times = []
    for deploy in successful_deploys[:20]:  # Sample last 20
        # In real implementation: get commit time from GitHub API
        # lead_time = deploy_time - commit_time
        lead_times.append(120)  # Example: 2 hours average
    
    avg_lead_time = sum(lead_times) / len(lead_times) if lead_times else 0
    
    if avg_lead_time <= 60:
        lt_level = "Elite (< 1 hour)"
    elif avg_lead_time <= 1440:
        lt_level = "High (< 1 day)"
    elif avg_lead_time <= 10080:
        lt_level = "Medium (< 1 week)"
    else:
        lt_level = "Low (> 1 week)"
    
    # 3. MEAN TIME TO RECOVERY (MTTR)
    # Get incidents from CloudWatch alarms or PagerDuty
    cloudwatch = boto3.client('cloudwatch')
    
    alarms = cloudwatch.describe_alarm_history(
        AlarmName='production-error-rate',
        HistoryItemType='StateUpdate',
        StartDate=start_date,
        EndDate=end_date
    )
    
    mttr_minutes = 45  # Example: 45 minutes average
    if mttr_minutes <= 60:
        mttr_level = "Elite (< 1 hour)"
    elif mttr_minutes <= 1440:
        mttr_level = "High (< 1 day)"
    elif mttr_minutes <= 10080:
        mttr_level = "Medium (< 1 week)"
    else:
        mttr_level = "Low (> 1 week)"
    
    # 4. CHANGE FAILURE RATE
    failed_deploys = [
        e for e in executions['pipelineExecutionSummaries']
        if e['status'] == 'Failed'
        and start_date <= e['lastUpdateTime'].replace(tzinfo=None) <= end_date
    ]
    
    total_deploys = len(successful_deploys) + len(failed_deploys)
    cfr = (len(failed_deploys) / total_deploys * 100) if total_deploys > 0 else 0
    
    if cfr <= 5:
        cfr_level = "Elite (0-5%)"
    elif cfr <= 10:
        cfr_level = "High (5-10%)"
    elif cfr <= 15:
        cfr_level = "Medium (10-15%)"
    else:
        cfr_level = "Low (> 15%)"
    
    return {
        "period": f"{start_date.date()} to {end_date.date()}",
        "iso9001_clause": "6.2 - Quality Objectives",
        "metrics": {
            "deployment_frequency": {
                "value": f"{deployment_frequency:.2f} deploys/day",
                "level": df_level,
                "target": "High or Elite"
            },
            "lead_time_for_changes": {
                "value": f"{avg_lead_time:.0f} minutes",
                "level": lt_level,
                "target": "High (< 1 day)"
            },
            "mean_time_to_recovery": {
                "value": f"{mttr_minutes:.0f} minutes",
                "level": mttr_level,
                "target": "Elite (< 1 hour)"
            },
            "change_failure_rate": {
                "value": f"{cfr:.1f}%",
                "level": cfr_level,
                "target": "Elite (0-5%)"
            }
        }
    }


if __name__ == "__main__":
    metrics = get_dora_metrics(days=30)
    print(json.dumps(metrics, indent=2))
    
    # Export for ISO 9001 management review
    with open(f"quality-report-{datetime.now().strftime('%Y%m')}.json", "w") as f:
        json.dump(metrics, f, indent=2)
```

## Clause 8.7 — Control of Nonconforming Outputs (Bug Management)

```yaml
# Jira workflow for ISO 9001 nonconforming output control
# Every bug is a "nonconformity" that must be tracked and closed

bug_management_process:
  
  detection:
    sources:
      - "Automated tests (CI/CD pipeline)"
      - "Production monitoring (Grafana alerts)"
      - "Customer reports (support tickets)"
      - "Security scans (Trivy, SonarQube)"
    
    classification:
      Critical: "System down or data loss → fix within 4 hours"
      High:     "Feature broken for many users → fix within 24 hours"
      Medium:   "Partial impact → fix within 7 days (next sprint)"
      Low:      "Minor issue → backlog, prioritize when available"
  
  jira_workflow:
    states:
      - Open (detected)
      - In Investigation (root cause analysis)
      - In Fix (being resolved)
      - In Review (PR submitted)
      - In Testing (QA validates fix)
      - Closed (fix verified in production)
    
    required_fields:
      - Root cause (WHY did this happen?)
      - Fix description (WHAT was changed?)
      - Test evidence (HOW was the fix verified?)
      - Prevention measure (HOW to prevent recurrence?)
  
  iso9001_evidence:
    - Bug count by severity per sprint
    - Time to close (vs SLA targets)
    - Recurrence rate (same bug appearing twice)
    - Root cause categories (trending analysis)
```

```bash
#!/bin/bash
# quality-report-generator.sh
# ISO 9001 Clause 9.1.1 — Monitoring and Measurement

REPORT_DATE=$(date +%Y-%m)
OUTPUT="quality-report-$REPORT_DATE.md"

cat > $OUTPUT << EOF
# Quality Report — $REPORT_DATE
ISO 9001:2015 — Clause 9.1.1 Monitoring and Measurement

## 1. Deployment Quality (Clause 8.6)
EOF

# Get pipeline success rate from CodePipeline
TOTAL=$(aws codepipeline list-pipeline-executions \
  --pipeline-name production \
  --query 'length(pipelineExecutionSummaries)' \
  --output text)

FAILED=$(aws codepipeline list-pipeline-executions \
  --pipeline-name production \
  --query 'pipelineExecutionSummaries[?status==`Failed`] | length(@)' \
  --output text)

SUCCESS_RATE=$(echo "scale=1; (($TOTAL - $FAILED) / $TOTAL) * 100" | bc)

cat >> $OUTPUT << EOF

- Total deployments: $TOTAL
- Failed deployments: $FAILED
- **Deployment success rate: $SUCCESS_RATE%**
- Target: > 95%

## 2. Test Coverage (Clause 8.3.5)
EOF

# Get SonarQube coverage from API
COVERAGE=$(curl -sf "http://sonarqube:9000/api/measures/component?\
  component=my-app&\
  metricKeys=coverage,duplicated_lines_density,code_smells" \
  -u admin:$SONAR_TOKEN | jq '.component.measures[] | select(.metric=="coverage") | .value' -r)

cat >> $OUTPUT << EOF

- Code coverage: $COVERAGE%
- Target: > 80%

## 3. Security Quality (Clause 8.3.3)
EOF

# Critical/High vulnerabilities from Security Hub
CRITICAL=$(aws securityhub get-findings \
  --filters '{"SeverityLabel":[{"Value":"CRITICAL","Comparison":"EQUALS"}],"WorkflowStatus":[{"Value":"NEW","Comparison":"EQUALS"}]}' \
  --query 'length(Findings)' \
  --output text)

cat >> $OUTPUT << EOF

- Open CRITICAL vulnerabilities: $CRITICAL (target: 0)

## 4. Incident Quality (Clause 8.7)
- See PagerDuty monthly incident report

## 5. Customer Satisfaction (Clause 9.1.2)
- Error rate: see Grafana dashboard
- P95 latency: see Grafana dashboard

## Next Review Date
$(date -d '+1 month' +%Y-%m-01)

ISO 9001:2015 Clause 9.3 — Management Review
EOF

echo "Quality report generated: $OUTPUT"
```

## Interview Questions — ISO 9001

**Q: How does CI/CD relate to ISO 9001?**
```
CI/CD IS the ISO 9001 quality system for software:

ISO 9001 says: "Control the release of products to ensure requirements are met"
CI/CD does:   Quality gates before every deployment
              - Tests must pass (functional requirements met)
              - Security scan must pass (security requirements met)
              - Code review approved (peer validation)
              - Staging validated (system tested end-to-end)

ISO 9001 says: "Maintain documented information as evidence"
CI/CD does:   Every pipeline run is logged with its test results,
              scan results, and who approved it — permanent audit trail

ISO 9001 says: "Continual improvement"
CI/CD does:   DORA metrics show improvement trends over time
```

**Q: What is the PDCA cycle in DevOps?**
```
Plan  → Sprint planning (what will we build? what does success look like?)
Do    → Development + CI/CD (build it, test it, deploy it)
Check → Monitoring + reviews (is it working? DORA metrics, error rates)
Act   → Retrospectives + postmortems (what to improve next sprint?)

The PDCA cycle runs at multiple speeds in DevOps:
  Per commit   → CI pipeline (minutes)
  Per sprint   → Retrospective (2 weeks)
  Per quarter  → Architecture review (3 months)
  Per year     → ISO 9001 management review (12 months)
```
